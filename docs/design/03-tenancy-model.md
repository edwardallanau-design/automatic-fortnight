# Tenancy & Isolation Model

**Strategy (rewritten 2026-08-03 — trigger fired: pilot client `kapeadri` deployed as a second real instance).** Deployment-per-tenant, branch-per-tenant: each client gets its own long-lived Git branch, own Vercel project, own Neon database, own credentials. No shared schema, no tenant-scoping column, no per-request tenant resolution, and — this round's actual decision — **no shared codebase-in-lockstep either**: a client branch does not automatically track `main`.

**Isolation axis: database-per-tenant.** Each client's data lives in its own Postgres instance; there is no code-level tenant boundary to get wrong, because there is no multi-tenant code at all. This is the same "db-per-tenant" option `03`'s original draft named as a candidate, now actually chosen.

**Code axis: branch-per-tenant, not `main`-per-tenant.** This is the part that changed from the internal pipeline's original plan (`docs/superpowers/specs/2026-07-08-dev-preprod-prod-pipeline-design.md` §4, which assumed every client instance tracks `main` directly with zero divergence). The internal `dev → preprod → main` pipeline still exists for the vendor's own product development. Each client gets an additional long-lived branch (`client/<name>`, e.g. `client/kapeadri`) that its dedicated Vercel project tracks instead of `main`. Promotion is one-directional and explicit: `main → client/<name>` is a plain merge, done as an extra step alongside every `preprod → main` promotion (not automatic, not a separate schedule) — see the pipeline design doc's amended §4/§5 for the mechanics. A client branch never merges back into `main`; any code driven by one client's real usage that turns out to be generally useful is re-implemented against `main`'s own state, not cherry-picked backward.

**Why branch-per-tenant over direct-`main` tracking.** A dedicated client instance needs a moment of human control between "a change is good enough for the vendor's own `preprod`" and "this specific paying client's live restaurant gets it mid-service" — a bad release hitting a real pilot during business hours is a different (and worse) risk than the same release reaching the vendor's own `dev`/`preprod`. Direct-`main`-tracking (Vercel's per-branch deploy triggering on every push) removes that control point entirely. The cost accepted for this: someone has to remember to run the `main → client/<name>` merge step, so a client instance can silently fall behind if that promotion step is skipped enough times — mitigated by making it a checklist line item on every promotion to `main`, not a separately-scheduled task with its own cadence to forget.

**What would invalidate this.** (a) More than a handful of client branches, at which point per-branch manual promotion stops scaling and this should move to some form of release-train tooling or back to direct-`main` tracking with a staged-rollout/feature-flag gate instead of a branch gate. (b) A client needing isolation deeper than "separate deployment + separate DB" — e.g. actual per-tenant data-model changes, not just separate infra — which would require this file's isolation-axis section to be revisited independent of the code axis above.
